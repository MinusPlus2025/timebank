## A. 对比赛的理解

1. **Monad 想听什么**：官方命题是“What becomes possible on Monad?”。所以评委的第一个问题大概率是：“这个东西放到以太坊 L2 或 Solana 上为什么不行或不够好？”。Monad 的卖点（ASSUMPTION，实现前要对照 docs.monad.xyz 核实）：
   - 约 400ms 出块、约 800ms 最终性 → 交互可以做到“点了就到账”
   - 高吞吐（官方宣传约 10,000 TPS）+ 并行执行 → 大量用户同时写链也不会拥堵
   - 极低 gas → 每秒、每次点击都上链在经济上可行
   - 完全兼容 EVM 字节码 → Solidity、Foundry、viem 等工具直接能用，开发风险低
   - P256 预编译（RIP-7212）→ 手机 Passkey / Face ID 签名可以直接在合约里验证（官方在赛道 4 点名了 P256/WebAuthn）
   - ERC-8004（Trustless Agents）、Encrypted Mempools 也被官方点名
2. **奖项结构**：4 个赛道各 3 个 $10k，另有一个总冠军。每个项目只能报一个赛道（二手）。每个赛道取前三，比拼的是能不能在本赛道排进前 3，不需要全场第一。
3. **评审节奏**：评审期 2 周，项目可能很多。评委大概率先看 3 分钟视频和 README 首屏。所以“30 秒内看懂”比功能多重要得多。

## C. 评审逻辑假设

[二手] 主赛道 5 项各 20%：**产品质量与完成度 / 技术水平 / Monad 集成 / 赛道契合 / 创新与影响**。

ASSUMPTION（我们的判断，用来指导取舍）：
- **完成度是最便宜的分**。大量黑客松作品在最后一周烂尾，一个能真正点开、能用、能部署的产品自动排在前一半。
- **“Monad 集成”这一项会筛掉一半人**。只是“部署在 Monad 上”的项目得不了高分；体验本身依赖速度、吞吐或 P256 的项目才能拿满分。最好的证明是 Demo 里出现一个**在其他链上明显会卡顿或太贵**的画面。
- **视频决定第一印象**。3 分钟里要在前 20 秒出现 wow moment。
- **评委会怀疑造假**。链上交易要能在区块浏览器里查到，合约要开源、要 verify。
- 时间这么短，“技术水平”分不要靠复杂度拿，要靠**干净的合约 + 测试 + 真实链上数据**拿。

## E. 机会空间（5 个，本质不同）

每个空间都是 IDEA，用一个具体示例来说明。评估维度按你的 9 个问题。

### E1. 每秒结算的消费支付（赛道 2：消费产品与支付）
**示例：“Meter”，按秒付费**。直播、音乐、1 对 1 咨询、共享充电、Wi-Fi 等场景，用户按住按钮就**每秒真实上链付一次钱**，松手就停。不需要预存、不需要支付通道，屏幕上的计费表和链上余额同步跳动。
- **用户**：内容创作者、按时间收费的服务者，以及不想买月卡的消费者
- **真实问题**：订阅制门槛高，按次付费又太粗；用户想“用多少付多少”
- **为什么需要 Monad**：每秒一笔链上交易，只有在亚秒出块 + 极低 gas 时体验和成本才都成立。在以太坊 L1 不可能；在一般 L2 上通常要靠状态通道或链下记账
- **独特机制**：不用通道，直接用链上微交易按秒计量；可以配合 Passkey（P256）让用户不装钱包、用 Face ID 授权一个限额 session
- **Wow moment**：观众用手机扫码，Face ID 一次，计费表开始走，旁边的区块浏览器同步刷出一笔笔交易
- **30 秒记忆点**：“每一秒都是一笔真实的链上支付”
- **技术难点**：session key / 限额授权、前端和链上状态同步。Passkey 验签是加分项也是风险点
- **一人能否完成**：能。合约很小，主要工作在前端
- **赛道 / Bounty**：赛道 2；可能对上 Privy / Dynamic / MetaMask（钱包类）、Agora（稳定币）
- **风险**：流式支付（Sablier/Superfluid）是已知概念，必须靠“真实逐秒上链 + 无钱包体验”拉开差距

### E2. 秒级预测市场（赛道 1：链上金融与交易）
**示例：“Next 10 Seconds”**。针对一个实时数据（价格、比赛进程、直播里的事件）开 10 秒一轮的涨跌预测，链上下注、链上结算、自动开下一轮。
- **用户**：链上交易者、直播观众
- **真实问题**：现有预测市场按天、按周结算，太慢，参与感弱
- **为什么需要 Monad**：10 秒一轮意味着下注、锁定、结算都要在几个区块内完成，大量用户同时下注需要高吞吐
- **独特机制**：极短周期 + 自动结算；可以接 Chainlink Data Streams 作为价格来源
- **Wow moment**：屏幕上倒计时，几十个地址同时下注，10 秒后自动派奖
- **30 秒记忆点**：“10 秒一轮、完全链上的预测市场”
- **技术难点**：预言机的延迟和可信度（这是最大风险）、结算 gas、防止抢跑
- **一人能否完成**：勉强可以，但预言机集成是不确定因素
- **赛道 / Bounty**：赛道 1；Chainlink、Nansen 可能相关
- **风险**：容易被看成赌博；类似的“二元期权”Demo 在各个黑客松很常见

### E3. Passkey 原生的 AI Agent 信任层（赛道 4：信任、身份与 AI 基础设施）
**示例：“Leash”，给 AI Agent 拴绳**。人类用 Passkey（P256，不需要助记词）给自己的 AI Agent 签一个**链上授权**：每天最多花多少、只能付给谁、什么时候失效。Agent 每次付款都由合约检查授权；人类随时用 Face ID 一键撤销。可以结合 ERC-8004 给 Agent 记链上身份和信誉。
- **用户**：让 AI Agent 代为付款（API 调用、购物、订阅）的个人和开发者
- **真实问题**：要么给 Agent 私钥（危险），要么每笔都人工确认（没法自动化）
- **为什么需要 Monad**：官方点名的 P256 + ERC-8004；Agent 高频小额付款需要低费用和快速确认，撤销必须马上生效
- **独特机制**：手机生物识别 → 链上可验证的限额授权 → Agent 自主花钱 → 一键撤销
- **Wow moment**：Agent 自己在付款，用户按一下 Face ID 撤销，下一笔付款在 1 秒内被链上拒绝
- **30 秒记忆点**：“Face ID 给 AI Agent 的链上刹车”
- **技术难点**：WebAuthn 签名格式解析 + P256 合约验签（有风险但有开源实现可以参考）
- **一人能否完成**：能，但 Passkey 部分要先做可行性验证（半天内）
- **赛道 / Bounty**：赛道 4（和官方描述高度吻合）；Privy、Dynamic、Kimi、Alibaba Cloud（AI 相关）可能相关
- **风险**：AI Agent 赛道人多；必须让 Demo 聚焦在“撤销”这个瞬间，不能做成泛泛的 Agent 平台

### E4. 实时注意力拍卖（赛道 3：社交、注意力与文化）
**示例：“Spotlight”**。一块公共大屏（直播间、活动现场、网页），屏幕上显示什么由观众**持续竞价**决定：每个区块重新结算一次谁占据屏幕，出价按秒扣费，收入分给主播或社区金库。
- **用户**：直播主、线下活动、社区
- **真实问题**：注意力是有价的，但现在的打赏和置顶都是一次性的、不透明的
- **为什么需要 Monad**：每个区块都重新拍卖、大量观众同时出价，正好对应高频 + 高吞吐。慢链上做不出“实时争夺”的感觉
- **独特机制**：连续时间的注意力市场（Harberger 税 / 按秒付费的屏幕租约）
- **Wow moment**：现场观众掏手机抢屏幕，大屏实时切换，链上每秒都有交易
- **30 秒记忆点**：“一块全体观众实时竞价的屏幕”
- **技术难点**：竞价规则设计（要简单、可解释），前端实时性
- **一人能否完成**：能
- **赛道 / Bounty**：赛道 3；钱包类 Bounty
- **风险**：录视频时需要“很多人同时参与”的效果，要用脚本模拟多个用户（在视频里如实说明）

### E5. 参数化微型保险（赛道 1 或 2）
**示例：“航班延误 / 下雨”即时理赔**。用户按小时买一份极小额保险，数据源触发条件后**在同一分钟内自动赔付**。
- **用户**：出行者、骑手、户外活动者
- **真实问题**：传统小额保险理赔慢、门槛高，没人买
- **为什么需要 Monad**：微额保单的 gas 必须远低于保费；即时赔付需要快速最终性
- **Wow moment**：触发条件，钱秒到账
- **技术难点**：可信数据源（Demo 里很可能只能用 mock 预言机，削弱可信度）
- **一人能否完成**：能，但 Demo 依赖模拟数据
- **风险**：概念在 2017 年就有（如 Etherisc），新意不足；“为什么是 Monad”的论证偏弱

### G. 预付款保护（IDEA，推荐候选）
**场景**：健身房、瑜伽馆、培训班、理发店、洗车店的预付卡和会员卡。
**真实问题**：消费者预付了一大笔钱，商家关门跑路，余额拿不回来。这是长期存在的社会问题（例如共享单车押金难退、教培机构倒闭；中国已经出台针对教培预付资金监管和预付式消费的规定）。具体数据引用前需要再核对来源。
**现有方案的缺陷**：银行资金存管门槛高、成本高，小商家用不上；消费者也看不到自己的钱到底在不在。
**链上机制**：
1. 消费者购买“10 次课”，钱锁在智能合约里，商家一分钱也拿不走
2. 每上一次课，消费者扫门口二维码签到，合约**当场**把 1 次课的钱付给商家
3. 没用完的余额，消费者**随时可以自己取回**，不需要商家同意
4. 所有余额公开可查：商家可以展示“已保护资金”作为信任标志，用来吸引顾客

**为什么必须上链**：要有一个商家卷不走、平台挪不动、谁都能核查的中立托管方。智能合约正好是这个角色，而且不需要银行开户和审批。
**为什么需要 Monad**：每次签到就是一笔结算。规模化以后（连锁门店、每天大量签到）需要高吞吐和几乎为零的手续费；在门口签到需要**1 秒内**确认，不能让顾客站在门口等十几秒。
**赛道**：Consumer Products & Payments（官方示例里有“可编程礼物、工资流、微型保险”，属于同一类可编程支付）
**Bounty**：Privy（顾客用邮箱登录，嵌入式钱包自动签署签到和退款，属于“不只是登录”的深度集成）、Envio（商家后台数据）、Crouton / Alchemy
**Wow moment**：“老板跑路了”→ 顾客点一下，剩余的钱 1 秒回到自己账户
**30 秒记忆点**：“预付卡，但老板卷不走你的钱”
**诚实的弱点**：
- 商家失去了一次性收大笔现金的好处。应对：允许商家设定一个小比例的首付款，或者把“资金受保护”当成营销卖点
- 普通顾客还不习惯用稳定币。应对：邮箱登录、看不到钱包；Demo 用测试网稳定币
**可完成度**：1 个合约（建卡、购买、签到、退款）+ 顾客端和商家端两个页面，3 天内可以做完

### H. 零工 / 工人工资防拖欠（IDEA，备选）
**场景**：零工、外包、临时工按天或按小时干活，结算周期长，经常被拖欠或克扣。
**链上机制**：雇主先把工资存进合约，工作期间按小时自动流向工人；已经干完的部分雇主收不回。
**为什么上链**：中立托管 + 自动执行。**为什么 Monad**：按分钟流式结算几乎零成本。
**弱点**：“工资流”是已知概念（Sablier、Superfluid）；真实工人使用加密货币的门槛更高。

### I. 群体公共资金透明（IDEA，备选）
**场景**：班费、社团经费、合租、小型众筹，钱由一个人保管，不透明，容易起纠纷。
**链上机制**：钱进共享合约，支出要多人确认，每一笔都公开可查。
**弱点**：Monad 的速度优势体现不出来（多签在任何链上都能做），“为什么需要 Monad”这一项拿分低。

## 第四轮：避开同质化（2026-10-10）

用户反馈：前几轮思路雷同，很多人会这么想。
**原因复盘**：前几轮都是从加密货币的老套路出发（托管、流支付、抢购），再去找一个场景套上去。这些套路几乎每个参赛者都会想到。
**新方法**：从两个方向反推。
1. **2026 年才出现或才变严重的问题**（AI 深度伪造、AI Agent 替人花钱），而不是十年前就有人用区块链做过的问题
2. **Monad 官方点名、但大多数人嫌难不愿碰的能力**：P256 / WebAuthn 预编译（让手机 Face ID / 指纹签名直接在链上验证）、亚秒级最终性

### J. “真的是你吗？”：对抗 AI 换脸 / 换声诈骗的真人验证（IDEA，推荐候选）
**真实问题**：AI 已经能克隆亲人或老板的声音和视频，再打电话、开视频会议，要求紧急转账。公开报道的案例有：2024 年香港一家跨国公司员工在“多人视频会议”中被深度伪造骗走约 2 亿港元；2023 年内蒙古包头 AI 换脸诈骗案。（引用前再核对来源）
**为什么现有办法不够**：家人之间约定“暗号”，容易忘、容易被套话；看视频辨真假已经不可靠；各个 App 各自为政，谁都不是中立的身份方。
**机制**：
1. 家人或团队成员各自用手机 Face ID 注册一个 Passkey，公钥记在链上的“信任圈”合约里。不需要助记词，不需要钱包
2. 接到可疑电话或消息，点“验证他是本人” → 对方手机弹出确认 → 对方刷 Face ID → 签名**在链上用 Monad 的 P256 预编译验证** → 约 1 秒后你的屏幕变绿或变红。骗子能克隆声音，但没有对方手机里的私钥
3. （可选）转账防护：给圈内成员转账只能转到他登记的地址；“我换卡了，打到这个新账户”这类改地址操作，需要 24 小时延迟加另一位成员确认。直接破解最常见的诈骗话术
**为什么必须上链**：身份公钥和验证记录要放在一个任何公司都改不了、任何 App（银行、支付、公司财务）都能查询的中立地方；丢手机后的撤销和恢复由圈内其他成员在链上完成，不依赖某家公司的客服。
**为什么需要 Monad**：P256 预编译让 Face ID 签名在链上验证变得便宜；亚秒级最终性让“通话过程中当场验证”真正可用，这在 12 秒出块的链上体验很差。
**赛道**：Trust, Identity & AI Infrastructure（官方列了 Proof of Personhood，并点名了 P256 / WebAuthn）
**Bounty**：Mera（Passkey-only onboarding，$5k，天然契合）或 Privy / Dynamic；Crouton / Alchemy
**Wow moment**：一段模仿“妈妈”声音的 AI 语音要钱 → 点“验证” → 真妈妈的手机刷 Face ID 变绿；骗子那边永远是红色
**30 秒记忆点**：“AI 能模仿你妈的声音，但模仿不了她的 Face ID。”
**诚实的弱点**：
- 对方必须能接收验证请求。不过“验证不了”本身就是一个强烈的危险信号
- 技术难点是 WebAuthn 签名的格式解析和 P256 预编译调用，需要 Claude 先用半天做可行性验证
- 竞品：聊天软件的“安全码”。差异在于：中立、跨 App、和资金规则绑定
- **安全边界（用户追问“Face ID 能不能被模仿”后补充）**：
  - 安全性不来自“脸”，而来自手机安全芯片里**导不出来的私钥**。Face ID 只是本机解锁这把私钥的开关
  - 远程的 AI 换脸、换声对它无效：骗子不在对方手机前；而且 iPhone 的 Face ID 用红外 3D 深度识别，照片和屏幕上的视频都骗不过（ASSUMPTION：精确数据引用前核对 Apple 官方安全白皮书）
  - 真实风险 1：**手机被偷，同时锁屏密码泄露**（Passkey 允许用锁屏密码代替刷脸）。应对：圈内其他成员可以在链上一键吊销这台设备
  - 真实风险 2：**Apple / Google 账号被盗**（Passkey 默认通过 iCloud 钥匙串等云端同步）。应对：新设备加入要经过圈内成员确认，并在链上公开记录
  - 真实风险 3：**骗子诱导真人本人去点确认**。应对：验证请求写明“谁、在什么时候、为什么在验证你”，有效期 60 秒，而且只对这一次请求有效
  - 结论：不是绝对安全，而是把攻击门槛从“网上下载 3 秒语音”提高到“偷到对方手机并解锁”。这一点要在 Pitch 里诚实说明

#### J 的使用场景与用户动机（用户追问“场景在哪里、用户为什么用”后补充）
**诚实结论**：“家庭防诈骗”需求真实，但有冷启动问题：双方都必须**事先**注册，而最容易被骗的老人恰恰最难被说服提前安装。所以家庭场景不适合作为第一批用户。

按“谁痛、谁付钱、谁能强制推行”重新排序：

| 场景 | 谁在用 | 什么时候用 | 为什么愿意用 | 冷启动难度 |
|---|---|---|---|---|
| **1. 公司付款指令核验** | 小公司、外贸公司的财务和出纳 | 老板或高管通过电话、视频、微信、邮件要求紧急转账 | 一次被骗就是几十万到上亿；公司可以用制度强制推行（“超过 X 元必须验证”）；链上验证记录可以留作审计证据 | 低：老板一句话全员安装 |

**用户为什么不用现有办法**：
- 回拨电话：号码可以伪造，账号可能已经被盗
- 口头暗号：会忘、会被套话，也没有记录
- 各家 App 的认证：只在自己的 App 里有效，跨公司、跨平台用不了
- 本方案：一次刷脸、1 秒出结果、跨任何平台、留下不可篡改的记录

### K. 骑手 / 司机的“不可篡改工作记录”（IDEA，备选）
**真实问题**：外卖骑手、网约车司机被平台算法判定超时罚款，但所有数据都在平台手里，劳动者没有证据。

**弱点**：属于 DePIN 赛道，已经很拥挤；Demo 只能模拟硬件。

## J 方向延展：功能性 + 艺术性（IDEA，待用户确认）

### 核心概念：「印」——数字时代的印章
- **叙事**：两千年来，人类一直用印章证明“这是我本人”（中国的印章、欧洲的火漆封印），讲究“见印如见人”。AI 时代，脸和声音都能伪造，需要一枚新的印章：只有你的手机能盖出来、链上人人可查。
- **一句话**：AI can fake your face. It can't fake your seal.（AI 能伪造你的脸，伪造不了你的印。）
- 候选名：**Seal / 真印 TrueSeal / 见印 SeenSeal**（待定）

### 艺术性 = 功能性：生成式印章
- 每次验证成功，用链上签名和交易哈希**生成一枚独一无二的印章图案**（篆刻风格的方形印，或者圆形火漆印）
- **功能作用**：双方屏幕上出现**同一枚**印章，肉眼一比就知道是不是同一次真实验证（相当于把聊天软件的“安全码”做成艺术品）。骗子伪造的页面拿不出与链上一致的印章
- 印章可以在区块浏览器里溯源：图案 ↔ 交易 ↔ 签名者
- 视觉风格：朱砂红、宣纸白、黑；验证中是“落印”动画，成功时“盖章”并配一声清脆的音效

### 功能清单（按优先级）
| 优先级 | 功能 | 说明 |
|---|---|---|
| **必须** | 刷脸注册 | Passkey，不需要钱包和助记词，公钥登记上链 |
| **必须** | 发起验证 | 生成一个链接，可以发到微信、Telegram、邮件等任何地方，对方打开即可，不用装 App |

| 应该 | 验证后付款 | 付款绑定验证：资金只有在指定的人盖印后才放行（对应“老板要求转账”场景） |

## 第五轮：真实需求 × 差异化（2026-10-10）

用户反馈：真印“大家很容易想到”，要同时满足真实需求和差异化。

**差异化测试**：想象 300 个参赛团队，**会不会有 10 个以上的团队做同一件事？** 会的话就不算差异化。
- 支付、托管、预测市场、AI Agent 钱包、Passkey 身份：会，不合格
- 真正差异化的点子通常来自**加密圈不熟悉、但现实中真实存在的领域**

### M. 链上时间银行：今天陪老人 1 小时，将来换回 1 小时（IDEA，推荐候选）
**真实需求**：
- 老龄化是全球问题（中国、日本、韩国、欧洲）。“时间银行”是已有的社会制度：志愿者照护老人的时长存起来，将来自己老了，再兑换别人的照护
- 现实案例（引用前要核对来源）：日本的 Fureai Kippu（1990 年代起）、瑞士圣加仑的 Zeitvorsorge、中国南京等地的时间银行试点
- **核心痛点**：这是一个跨越**几十年**的承诺，但记录掌握在单个社区、机构或 App 手里。机构撤并、App 停运、换了城市，时长就没了，所以人们不敢存。另外还有刷时长造假、各地互不承认的问题

**链上机制**：
1. 志愿者上门服务，开始和结束时**志愿者和老人双方**都用手机刷脸（Passkey）确认，防止编造时长
2. 每次确认就是一笔链上记录：时长归志愿者所有，任何机构都删不掉
3. 换城市、换机构，凭同一个身份**跨机构兑换**
4. 机构的服务总量、兑换率公开可查，政府和公益方可以按真实数据拨款

**为什么必须上链**：唯一能比任何单个运营方活得更久、并且被多个互不隶属的机构共同承认的记录，就是公共链。“几十年的承诺”正好对上“没有人能关掉的账本”。
**为什么需要 Monad**：
- 每次上门的开始和结束都要上链，大规模时是海量小额记录，公益机构付不起高手续费
- 老人在门口刷脸确认，要 1 秒内出结果
- 双方 Passkey 签名用 Monad 的 P256 预编译验证（同样需要技术验证）

**赛道**：Social, Attention & Culture（社区与社会关系），或 Consumer Products
**Bounty**：Mera / Privy（老人不可能记助记词，Passkey 免钱包注册正好是刚需）
**Wow moment**：“这家社区服务中心关门了”→ 志愿者的 120 小时依然在链上，换一个城市当场兑换
**30 秒记忆点**：“你今天陪伴的时间，30 年后还在。”
**差异化**：300 个团队里很难有第二个做时间银行
**诚实的弱点**：
- 机制上和“预付卡防跑路”同构（机构倒闭、资产还在），但领域完全不同，叙事是“代际互助”而不是“消费维权”
- “公共链 30 年后还在”是所有区块链共有的论点，Monad 特有的论点要靠高频确认和低成本支撑
- 要防止双方串通刷时长：可以设每天上限，并加机构抽查签名

### N. 骑手互助保障池（IDEA，备选）
**真实需求**：外卖骑手、快递员受伤以后往往没有保障，平台保险覆盖有限、理赔慢。
**链上机制**：每接一单自动扣 1 分钱进互助池；受伤后由附近骑手投票加小额快速理赔；资金全部公开透明。
**为什么需要 Monad**：每单都存一笔，百万骑手每天千万级的小额交易。
**差异化**：中等（链上互助保险以前有人做过，但骑手这个具体人群少见）。
**弱点**：保险和互助涉及监管；理赔欺诈防范比较复杂。

### M 的场景扩展（用户要求：多场景、有社会意义、普遍）
**统一理念**：互相帮助的时间是一种资产，可以存、可以转、几十年不丢。**1 小时 = 1 小时**：医生和学生的一小时等值（时间银行的核心价值观，也是社会意义所在）。
**设计原则**：底层只有一套机制（双方刷脸确认 → 时长上链 → 跨社区兑换 / 转赠），各场景只是“社区类型 + 服务标签”不同，**多做场景几乎不增加开发成本**。

| # | 场景 | 谁 | 真实痛点 | 普遍性 |
|---|---|---|---|---|
| 1 | 养老陪护 | 志愿者 ↔ 老人 | 几十年的承诺，记录却靠单一机构 | 全球老龄化 |
| 2 | **学生 / 青年志愿时长** | 学生、学校、志愿组织 | 升学和求职都看志愿时长，但证明分散在各个平台，还有造假 | 极广：中国志愿服务记录、美国升学 community service 等（引用前核对） |
| 3 | 邻里互助 | 同一小区或街区的居民 | 修东西、取快递、遛狗、帮老人买菜，想互助却没有信任和记账机制 | 城市普遍 |
| 4 | 育儿互助 | 家长之间 | 托育又贵又难，家长轮流接送、看孩子，谁欠谁说不清 | 普遍；经济学里著名的“国会山保姆合作社”案例（引用前核对） |
| 5 | 陪诊 / 病友互助 | 独居者、慢病患者、残障人士 | 看病没人陪、盲人出行需要陪伴 | 独居人口增长 |
| 6 | 技能交换 | 任何人 | 教语言、辅导功课、教手机使用，用时间换时间而不是钱 | 普遍 |
| 7 | 应急与灾害志愿 | 跨机构的志愿者 | 救灾时志愿者在多个组织之间流动，时长和资质互不承认 | 全球 |
| 8 | 企业志愿 / ESG | 公司员工 | 公司要披露员工志愿时长，但数据难以核实 | 潜在付费方（商业模式） |

**杀手级功能：时长转赠给家人（异地互助）**
- 子女在上海做志愿服务，把攒下的时长**转给老家的父母**，父母在当地兑换陪诊、上门照护
- 对应留守老人、异地养老这个普遍痛点，也是 Demo 里最打动人的一幕
- 时长只能**转赠，不能买卖**（坚持“时间不是商品”，也避开金融监管问题）

**Demo 建议（3 个场景就够，不要贪多）**：
1. 学生志愿（最普遍）：学生在社区服务 2 小时，双方刷脸，时长上链；学校一键核验，假证明无处可藏
2. 邻里互助：帮邻居修水管 1 小时，换邻居教孩子英语 1 小时
3. 转赠（最打动人）：上海的女儿把 10 小时转给老家的妈妈 → 机构关门，记录依然在 → 妈妈在当地兑换陪诊

**候选名字**：光阴银行 / OneHour 一小时 / Hourglass（待定）

### M 的家庭场景扩展（用户追问：情侣之间、子女之间）
| # | 场景 | 真实痛点 | 现实依据（引用前核对原文） |
|---|---|---|---|
| 9 | **兄弟姐妹赡养父母** | 谁陪父母看病、谁照顾得多，事后说不清，常常引发家庭矛盾甚至继承纠纷 | 中国《民法典》继承编规定，对被继承人尽了主要扶养义务的继承人，分配遗产时可以多分（约第 1130 条）；可信的照护记录有现实意义 |
| 10 | **情侣 / 夫妻的家务与育儿** | 家务、育儿等“隐形劳动”多由一方承担，却不被看见 | 《民法典》规定离婚时承担较多家务的一方可以请求补偿（约第 1088 条）；联合国等机构长期关注无偿照护劳动 |
| 11 | 子女陪伴父母 | 子女在外地，陪伴少，父母孤独 | 《老年人权益保障法》有“常回家看看”的条款 |
| 12 | 亲子陪伴券 | 孩子做家务换“爸爸陪我玩 1 小时”；父母兑现承诺 | 教育意义：守信、劳动、陪伴 |

**设计注意（诚实风险）**：
- **亲密关系里“记账”可能伤感情**。产品要定位成“看见和感谢彼此的付出”，而不是算账；默认不显示“谁欠谁”，只显示“我们一起付出了多少”
- **隐私**：公共链上任何人都能看到记录。家庭圈只上链匿名地址、时长和类别代码，不上链任何文字内容；更强的隐私（加密）放到未来规划
- 法律相关的用途（继承、离婚补偿）只能作为“可信记录有现实价值”的佐证，**不能宣传成法律证据**

**定位升级**：从“志愿者时间银行”升级为“**看见每一份付出的时间账本**”，覆盖三个圈层：
1. 家庭圈（情侣、兄弟姐妹、亲子）
2. 社区圈（邻里、育儿、陪诊、技能交换）
3. 社会圈（志愿服务、养老、救灾、企业志愿）

### 修正：学生志愿场景降级（用户指出“学生志愿一般都有机构开的证明”）
- 用户说得对。中国有官方的全国志愿服务信息系统（中国志愿服务网），还有共青团等平台记录时长；国外也多由组织负责人签字证明。**正式志愿服务的证明问题基本已经有机构在解决**，之前说“证明分散、造假”是夸大了
- 结论：学生志愿、企业志愿这类**有机构背书**的场景不再作为卖点，从 Demo 里移除

**由此得到更清晰的核心洞察**：
> 有机构的付出，机构会证明；**没有机构的付出，没有人记录。**
> 而生活中最大量的照护和互助恰恰是非正式的：家人之间、兄弟姐妹之间、邻里之间、朋友之间。

**为什么这些场景必须上链**：家庭和邻里之间**没有中立的第三方**。记录放在任何一方手里（比如某个兄弟管着的表格或群聊）都可以被改、被删；双方刷脸确认、谁也改不了的链上记录，正好补上“中立第三方”这个空位。

**Demo 调整为**：
1. 兄弟姐妹照顾父母（家庭圈）
2. 邻里互助：修水管换教英语（社区圈）
3. 女儿把时长转赠给老家的妈妈 → 妈妈在当地兑换陪诊（跨圈层）

**定位一句话**：「记录那些没有机构会证明的付出」

### 修正：尊重文化与伦理，不是什么都要“证据”（用户指出）
用户说得对。之前提出的“兄弟姐妹赡养记录、夫妻家务记账、用于继承或离婚”**撤回**。理由：
- 在很多文化里，家人之间的付出**本来就不该被计量**：中国讲孝道和“家和万事兴”，日本有“恩”与“义理”，很多文化的互惠是默契而不是账本。把亲情变成证据，会伤害它本来要守护的关系
- 很多宗教和传统认为善举应当**匿名**：伊斯兰教提倡私下施舍，基督教有“不要叫左手知道右手所做的”，佛教讲“无相布施”
- 把产品定位成“证据工具”，会把人际关系推向对抗

**新的边界：陌生人和邻里之间可以记时间；家人之间不记账，只传递。**

| 关系 | 怎么做 | 原因 |
|---|---|---|
| 陌生人、邻里、社区 | 可以记录互助时间、跨社区兑换 | 时间银行在很多文化中已经被接受；陌生人之间需要信任机制 |
| 家人 | **不在家人之间记录或计算任何东西**；家人只是**受益方**：你在社区里攒的时间，可以送给远方的父母，让当地的人替你照顾他们 | 契合孝道等文化价值：“我不在身边，但有人替我陪你” |
| 匿名善举 | 可以把时间**匿名捐**进社区公共池，给最需要的人 | 尊重“施恩不图报”的传统 |

**产品伦理原则（写进 README，作为 Pitch 亮点）**：
1. **由受助者发起感谢**，而不是帮助者索要记录。记录的本质是“谢谢你”，不是“你欠我”
2. **不显示谁欠谁，不做排行榜**
3. **双方都同意才记录**，任何一方都可以拒绝
4. **可以匿名**：可以匿名帮助、匿名捐赠
5. **每个社区自己定规则**：是否 1 小时 = 1 小时、是否允许兑换、是否只记感谢不记时长，由社区决定。这样产品能适应不同文化
6. **不作为法律证据宣传**；链上只存匿名地址、时长和类别，不存任何文字内容

**Demo 调整为**：
1. 邻里互助：帮邻居修水管 1 小时 → 邻居发起“谢谢你”，双方刷脸确认，时间上链
2. 匿名捐赠：把 5 小时匿名捐给社区公共池
3. 最打动人的一幕：在上海的女儿把攒下的时间送给老家的妈妈 → 当地的志愿者上门陪妈妈去医院 →“我不在你身边，但有人替我陪你”

### 评估：“帮助记住珍贵时刻 / 帮助失智老人回忆”是否合适（用户提问）
**结论：心意很好，但不适合作为核心；可以作为一个小而温暖的附加功能，前提是严格遵守隐私规则。**

**需求是真实的**：给失智或阿尔茨海默症老人做“回忆疗法”、生命故事册，是照护领域常用的方法（具体证据引用前核对）。

**不适合作为核心的原因**：
1. **区块链帮不上“记住”**：照片、语音这类回忆内容既不能也不应该放到链上（体积大，而且永久公开）。真正存回忆的是相册或网盘，链上只能存一个指纹，正好落入之前列出的弱项目类型“只是把哈希上链”。Monad 必要性很低
2. **伦理风险高**：
   - 失智老人可能**无法真正表示同意**
   - 健康状况属于最敏感的个人信息，**绝对不能上公共链**；链上记录永久不可删除，和“被遗忘权”冲突（例如欧盟 GDPR）
   - 评委很可能质疑：“为什么要把病人的信息放到区块链上？”
3. **范围膨胀**：3 天内再加一个产品，会拖垮完成度

**可以保留的温和版本（附加功能，可选）**：
- 每次互助结束时的“谢谢你”，自然会形成一条“谁在什么时候陪过你”的时间线
- **“陪伴记忆”视图**：老人或家属可以看到“这是小王，她来看过你 12 次”。帮助失智老人认出常来的志愿者，也让家属放心，同时防止陌生人冒充志愿者上门
- 可以给某次陪伴附一张照片或一段语音，**只存在家属自己的设备或加密存储里，可以随时删除，绝不上链，链上也不存它的哈希**
- 链上始终只有匿名的“某天，一次 1 小时的陪伴”
- 涉及失智老人时，由家属或监护人代为同意

**和名字的呼应**：“光阴银行”这个名字可以同时承载“存下的时间”和“留住的时光”。

### 先例调查与“链上是否必须”（用户提问，2026-10-10 网络搜索）
**有人做过吗？有，“区块链 + 时间银行”不是新概念：**
- 中国：蚂蚁区块链与南京合作的时间银行方案；志愿汇与 everiToken 的区块链志愿平台（2019 公告）；学术论文提出“公益时间链”。民政部 2018 年把时间银行纳入居家社区养老改革试点，青岛、上海、北京等地都有推进
- 海外：台湾 2022 年基于 MultiChain 的博士研究；英国 Timebanking UK 合作的“Tokenising Timebanking”研究（2023 年起）；Binghamton 大学的 BlendTBS 论文；Chronobank（2017，劳动时间代币，方向不同）
- **风险提示**：民政部、银保监会曾发文提醒，网上有人打着“时间银行”旗号搞投资诈骗。我们必须彻底避免任何代币投机、买卖的色彩

**这些先例意味着什么**：
- 好的一面：先例**证明需求真实**，政府和大公司都在投入
- 暴露出的空白：现有方案多是**联盟链或政府平台**，由单一城市或运营方掌控，跨城市不互认，用户不拥有自己的记录（北京有人大代表建议建立统一的时间储蓄运营机制，侧面说明各地互不相通）
- 坏的一面：**原创性从“强”下调为“中”**

**链上是必须的吗？诚实回答：不是在所有情况下都必须。**
| 情况 | 需要区块链吗 |
|---|---|
| 单一社区、单一运营方 | **不需要**，一个数据库就够 |
| 政府统一建全国平台 | 不需要公链（中心化方案是我们的主要替代品） |
| **多个互不隶属的机构要互认时长**，又不想把数据交给某一家 | **需要**，这是公链真正的价值 |
| **记录要比运营方活得更久**（几十年），并且由用户自己持有 | **需要** |
| 时长转赠给异地家人、在另一家机构兑换 | **需要**，属于跨机构场景 |

**Monad 必要性：中等偏弱（必须诚实面对）**
- 能讲的点：每次服务的开始和结束都要双方确认，规模化以后是海量小额写入，需要接近零的费用；在门口刷脸确认要 1 秒内出结果
- 弱点：时间银行不是一个“每秒都在交易”的场景，在其他低费用的链上也能做。评分中的“Monad 集成”可能拿不到高分

**与“真印”的对比**：
| | 时间银行 | 真印 |
|---|---|---|
| 真实需求 | 强（有政府试点佐证） | 强 |
| 原创性 | 中（有先例，但公链跨社区互认是空白） | 弱（容易撞题） |
| 链上必要性 | 中（跨机构互认时成立） | 中强 |
| Monad 必要性 | 中偏弱 | 强（P256 预编译 + 亚秒确认） |
| 情感与记忆点 | 强 | 强 |
